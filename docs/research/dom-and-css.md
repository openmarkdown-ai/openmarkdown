# Obsidian DOM and CSS contract for an open-source clone

What a browser clone of Obsidian must reproduce so that community themes and plugin `styles.css` files render unmodified.

Research date: 2026-09-13. Reference behaviour: Obsidian 1.13.x, the version the public docs and `obsidian.d.ts` 1.13.2 describe.

## 0. Sources and provenance rules (read first)

**Only public sources are used in this document.** An earlier draft extracted facts from Obsidian's installed application bundle. Obsidian's Terms of Service forbid reverse engineering except for non-commercial plugin development, so that material was withdrawn. The scratch copies were deleted, and nothing here depends on them. Every value and structure below carries one of the evidence tags in the table, and anything without public confirmation is marked **unconfirmed** or left out.

How the corpus evidence works. A class counts as confirmed to exist in Obsidian's DOM when it appears in selectors in several unrelated themes or plugins and is not plugin-prefixed. A nesting such as `.a > .b` or `.a .b` counts as confirmed when some theme or plugin selector writes that relation. The DOM skeletons in section B are generated by a script that checks every class, every same-element class pairing and every parent-to-child relation against the corpus, and prints the counts next to each element. They show what themes *assume* the DOM looks like, which is exactly the contract the clone must satisfy. They do not show Obsidian's implementation.

**Before shipping**, validate the skeletons against screenshots, or ask a volunteer who may lawfully inspect their own app to confirm open questions. The **Open questions** list in section E covers them.

## 1. Theme loading contract

### 1.1 Files and cascade

| Fact | Evidence |
|---|---|

| "You can override parts of a theme using snippets", so **snippets load after the theme** | [H] Glossary |

| Recommended guidance to theme authors: override general variables on `body`, colours on `.theme-light` / `.theme-dark`, and use `:root` sparingly | [D] Theme guidelines, Build a theme |

| "Native menus: menus will match the operating system. They will not be affected by your theme." A web clone always uses DOM menus | [H] Settings |

Clone order: `base.css` → plugin `<style>` elements (in enable order) → theme `<style>` → snippet `<style>` elements (sorted by filename, unconfirmed). Use real `<style>` elements rather than constructable stylesheets, so that Style Settings, which reads `/* @settings */` comments from `document.styleSheets`, keeps working. 18 of 23 sampled themes embed a `@settings` block [T 18].

### 1.2 The variable-override contract

The docs state the core rule: "By overriding the default values for the Obsidian CSS variables, you can create beautiful themes without the need for complex CSS selectors" [D]. The docs also warn that "the most common issues when maintaining a theme are due to broken selectors as a result of new versions of Obsidian, which may change class names and how elements are nested" [D]. So the clone must satisfy **two contracts**:

1. **Variables.** Every documented variable must exist and actually drive the matching visual property (section A).
2. **Selectors.** The class names, attributes and nesting that real themes target must exist (sections B and C).

Where Obsidian defines its defaults matters. Themes override on `body` and `.theme-*` [D, S]. If the clone defined its defaults on `:root`, a theme's `body {…}` override would still win, but a theme that writes `:root {--x}` expecting to beat a `body` default would behave differently. **Define defaults on `body` and `.theme-light` / `.theme-dark`**, which is the documented pattern.

### 1.4 CSS that the app reads back (inferred from how themes use it)

1. **Callout icon and colour.** `.callout[data-callout="x"] { --callout-color: …; --callout-icon: lucide-alarm-check; }` defines or overrides a callout. `--callout-icon` accepts a Lucide id **or an SVG string** such as `'<svg>…</svg>'` [H]. The renderer must therefore read the computed `--callout-icon` for each callout and render the icon from it.
2. **Graph colours.** The graph is drawn on a canvas, yet 6 themes style `.graph-view.color-fill`, `.color-fill-focused`, `.color-fill-tag`, `.color-fill-attachment`, `.color-fill-unresolved`, `.color-arrow`, `.color-circle`, `.color-line`, `.color-text`, `.color-fill-highlight` and `.color-line-highlight` using `color:` and `opacity:` only [T 6]. The docs list `--graph-*` variables [D]. **Inference:** the app reads the computed colour of hidden `.graph-view.color-*` elements. The clone should create such probes and read `getComputedStyle`.
3. **Canvas colours.** `--canvas-color-1`…`6` are documented [D], and `.canvas-node` / `.mod-canvas-color-N` selectors appear in themes [T].

## A. CSS variable catalogue

### A.0 What is and is not publicly documented

The developer docs list **682 variables** across 63 pages [D]. They publish **default values for 93 of them**: the colour palette, typography scale, spacing, radii, border width, layers, icon sizes, cursor and `--direction`. For the other 589 the docs give the name and a description but no default value. **This catalogue gives defaults only where the docs do.** Every other variable is marked `—`, so the clone must choose its own value (see section D) and calibrate it against public screenshots.

For each variable the table also reports how many of the 23 sampled themes **set** it and **read** it, and how many of the 34 plugins **read** it. Those counts are a priority list: a variable that 15 themes set must drive the right property, or those themes break.

### A.2 Typography facts from the docs

- `--font-interface-theme`, `--font-text-theme` and `--font-monospace-theme` are the documented *theme* font hooks: "Font used for UI elements / text in the editor / monospaced content" [D]. The Build a theme tutorial sets `body { --font-text-theme: Georgia, serif; }` [D].
- Use `--font-*` (relative) sizes in the editor and `--font-ui-*` (fixed) sizes for UI [D].
- `--bold-modifier` (1.6+) "stacks on top of other font weights"; recommended values are 100–300 [D].
- Undocumented but widely read: `--font-interface` [T 8, P 6], `--font-text` [T 9], `--font-monospace` [T 10, P 13], `--font-text-override` [T 8]. The clone must define these composite stacks. How they compose from `*-theme` and user overrides is **unconfirmed**; section D proposes one.

## B. DOM skeletons (evidence-checked against public theme and plugin CSS)

### B.0 How to read the skeletons

The skeletons below are generated from a specification by a script that checks each element against the 60-file public CSS corpus described in section 0. Closing tags are omitted, and indentation shows nesting. The comment on each line reports:

- `T n P m`: the smallest number of themes / plugins that use *each* of the element's primary classes. Bracketed classes such as `[is-active]` are optional state classes.
- `nest >a dB`: how many corpus files write the relation from the parent element's classes to this element, as a **direct child** (`>`) or as a **descendant** (`d`). `via grandparent` means the relation is only written with an intermediate element skipped.
- `nesting unconfirmed`, `same-element pairing unconfirmed` or `[attr] unconfirmed`: no corpus selector writes this relation, class pairing or attribute. The structure is plausible and consistent with names used in the docs and API, but **treat it as a hypothesis**.
- `# comments` cite API fields ([API] `obsidian.d.ts`) or docs where they apply.

What is confirmed from docs and API rather than CSS:

- `View.containerEl` holds the header and content: the Views guide builds content in `this.contentEl`, which is `ItemView.contentEl` [D, API].
- `ItemView.addAction(icon, title, cb)` returns the action element [API].
- `Plugin.addRibbonIcon(icon, title, cb)` and `Plugin.addStatusBarItem()` return elements. "Obsidian by default adds a gap between each status bar item" [D].
- `Modal` exposes `containerEl`, `modalEl`, `titleEl`, `contentEl` [API].
- `SuggestModal` exposes `inputEl`, `resultContainerEl` [API].
- `Notice` exposes `containerEl`, `messageEl` (1.8.7) and `noticeEl` (deprecated) [API].
- `HoverPopover` exposes `hoverEl` [API].
- `Setting` exposes `settingEl`, `infoEl`, `nameEl`, `descEl`, `controlEl`, `errorEl` (1.13) [API].
- `SettingGroup` exposes `listEl` (1.11) [API].
- `SettingPage` exposes `rootEl`, `titlebarEl`, `containerEl` (1.13) [API].
- Each component exposes its element: `ToggleComponent.toggleEl`, `DropdownComponent.selectEl` (an `HTMLSelectElement`), `SliderComponent.sliderEl` (an `HTMLInputElement`), `ButtonComponent.buttonEl` (an `HTMLButtonElement`), `ExtraButtonComponent.extraSettingsEl`, `SearchComponent.clearButtonEl`. ### B.4 Live Preview / Source editor: line and token classes

The editor is CodeMirror 6: `.cm-editor`, `.cm-scroller`, `.cm-content`, `.cm-line`, `.cm-gutters`, `.cm-cursor`, `.cm-selectionBackground` [T 10–20]. Markdown highlighting shows up in theme CSS in two forms:

- **line classes** on `.cm-line` (`HyperMD-*`), confirmed as on the same element as `.cm-line` in 5 themes;
- **token classes** on spans inside the line (`cm-*`).

Counts are themes / plugins using the class, followed by the same-element (`same`) and descendant (`d`) relations the corpus writes. The class *names* are confirmed. The exact pairing on one span is only confirmed where a `same` count is shown.

### B.6 `cssclasses`

The `cssclasses` property (a list; `cssclass` was deprecated in 1.4 and dropped in 1.9) "allows you to style individual notes using CSS snippets" [H]. The help example `.red-border img {…}` implies the classes land on an ancestor of the note's rendered content. Theme cssclasses such as Minimal's `.cards`, `.table-100` and `.img-grid` style both reading and editing views, so **put the classes on `.markdown-preview-view` and `.markdown-source-view`**. The exact element is unconfirmed; this placement follows the theme evidence.

### B.17 Icons

Public facts:

- Obsidian uses **Lucide**; supported ids go up to **v0.446.0** [D Icons, H Credits].
- `setIcon(parent, iconId)` "inserts an SVG into the element from an iconId" and does nothing for unknown ids. `getIcon(iconId)` returns an `SVGSVGElement` or null. `getIconIds()` lists registered icons [API].
- `addIcon(id, svgContent)` takes SVG *content* without the `<svg>` wrapper, drawn in a **`0 0 100 100` view box** [D, API].
- Rendered icons are `svg.svg-icon` [D Right-to-left: `.mod-rtl svg.svg-icon.left-icon`; T10].
- Icon ids appear as classes on the SVG with a `lucide-` prefix: themes target `.lucide-more-vertical`, `svg.lucide-chevrons-up-down` and similar [T]. Callout CSS uses ids such as `lucide-alert-circle` [H]. The help docs embed icons as `lucide-folder-open.svg`.
- Icons mirror automatically in RTL unless `transform: unset` [D].
- Sizing: set `--icon-size` on the container [D Icons guide]. Documented presets: `--icon-xs` 14px, `--icon-s` 16px, `--icon-m` 18px, `--icon-l` 18px, `--icon-xl` 32px, with stroke widths 2 / 2 / 1.75 / 1.75 / 1.25 px [D]. (The Icons guide example writes `--icon-size-m`, which does not match the reference table's `--icon-m`; treat that as a docs typo.)
- Lucide's own SVG attributes are 24×24, `stroke="currentColor"`, `stroke-width="2"`, round caps and joins [D Icons: design guidelines].

Clone rules: render Lucide 0.446.0 SVGs with `class="svg-icon lucide-<name>"`, accept ids with or without the `lucide-` prefix, and give `addIcon` icons `viewBox="0 0 100 100"` with `class="svg-icon <id>"`. The prefix-less form and the class of custom icons are **unconfirmed**. Obsidian also ships non-Lucide ids that themes reference as SVG classes, such as `right-triangle` [T4] (the collapse chevron) and `help` [T2]; which other ids exist is unconfirmed.

## E. Implementation checklist and open questions

### E.1 Checklist, in priority order (by how many themes break without it)

1. **Variables before selectors.** Define all 682 documented variables on `body` and `.theme-*`, using the docs' 93 published defaults. Make sure each one actually drives its property: a theme that sets `--tab-container-background` or `--nav-item-color` must see the effect. Also define the undocumented-but-read variables in A.4, the deprecated `-rgb`/`-hsl` aliases, and `--font-interface`, `--font-text` and `--font-monospace`.
2. **Body classes.** Set `theme-dark`/`theme-light`, a platform class, `is-mobile`/`is-phone`/`is-tablet` when relevant, `mod-rtl`, the frame and focus classes, and `show-inline-title`/`show-view-header`/`show-ribbon`.
3. **Top-40 classes in C.1** on the right elements, with the nesting in B (these are 14–23-theme classes): `markdown-rendered`, `markdown-preview-view`, `markdown-source-view`, `cm-s-obsidian`, `cm-line`, `callout*`, `workspace-*`, `nav-folder-title`/`nav-file-title` together with `tree-item-*`, `vertical-tab-*`, `checkbox-container`, `modal`, `menu`, `popover`, `status-bar`, `clickable-icon`, `is-active`/`is-collapsed`.
4. **Editor token classes (B.4).** Themes style headings, lists, tasks, quotes and code blocks almost entirely through `HyperMD-*` line classes and `cm-*` spans. A clone using stock `@codemirror/lang-markdown` must remap its highlight tags to these names and add the line decorations, including `data-task` on task lines.
5. **Attributes.** `data-type` on `.workspace-leaf-content` and `.workspace-tab-header`; `data-mode`; `data-callout`, `data-callout-metadata` and `data-callout-fold`; `data-task`; `data-path` on file-tree items; `data-property-key` and `data-property-type`; `aria-label` on icon buttons; `dir`.
6. **Stylesheet plumbing.** Use real `<style>` elements in the order base → plugins → theme → snippets, so Style Settings can parse `@settings`. Fire a `css-change` workspace event when styles change (unconfirmed name, but Style Settings expects a re-read hook).
7. **Read-back probes.** `--callout-icon` (a Lucide id or an SVG string) and `.graph-view.color-*`.
8. **Compatibility shims.** Render `r, g, b` callout colours; emit both `modal-close-button` and `modal-header-button`; optionally a legacy `.frontmatter-container`.
9. **Icons.** Lucide 0.446.0 as `svg.svg-icon.lucide-<id>`; `addIcon` with a 100×100 view box; RTL mirroring.
10. **Plugin API DOM fields** exactly as in `obsidian.d.ts` (B.0 list), because plugins append to `contentEl`, `controlEl`, `titleEl` and friends, and plugin CSS then targets `.setting-item-control`, `.modal-content`, `.view-content`.

### E.2 Open questions (not resolvable from public sources)

| # | Question | Why it matters | Suggested way to resolve lawfully |
|---|---|---|---|
| 1 | Default values of the ~589 undocumented-default variables (backgrounds, tabs, nav, headings, callouts …) | Visual parity with the default theme; themes that only partly override | Ask Obsidian to publish them, or calibrate from public screenshots; a volunteer's DevTools "Computed" panel counts as the user's own inspection and should be reviewed with counsel first |
| 2 | Plugin `styles.css` order relative to the theme | Cascade ties | Empirical: install a theme and a plugin with conflicting equal-specificity rules and observe which wins (black-box testing of visible behaviour) |
| 3 | Exact tokenizer span structure in Live Preview (which classes share a span; hidden-formatting behaviour) | Themes with compound selectors such as `.cm-formatting.cm-header` | Screenshot-driven testing with themes that use those selectors |
| 4 | Where `cssclasses` land (which ancestor) | Minimal's `.cards` / `.table-100` | Test with Minimal's documented cssclasses and compare against screenshots in its docs |
| 5 | The modal close-button class in current versions (`modal-close-button` vs `modal-header-button`) | 8 vs 2 themes | Emit both |
| 6 | Accent-shade derivation (`--color-accent-1/2`) and whether the user accent sets `--accent-h/s/l` inline on body | Accent hover colours | The docs describe the shades only as "shifted"; choose a formula |

### E.3 How to keep this current

Re-run the corpus scripts (evidence extraction, skeleton checker, table generator) when adding themes. Themes are the ground truth for what must exist. Track the developer docs repo (`obsidianmd/obsidian-developer-docs`, `en/Reference/CSS variables`) and `obsidian-api/CHANGELOG.md` for new or deprecated variables and DOM fields.
