# Web platform capabilities and data robustness

Research date: 2026-09-14. Scope: what a best-in-class browser Markdown app should use from the web platform (Part A), how browser and local-first note apps lose data and what this codebase does about it (Part B), and a prioritised change list (Part C).

This builds on [clipper-and-browser-fs.md §3](clipper-and-browser-fs.md#3-browser-filesystem-for-a-local-vault), which already covers the File System Access / OPFS support matrix, persistent permissions, FileSystemObserver record types, OPFS quotas and the adapter design. That material is summarised here, not repeated.

**Method.** Support data came from MDN, chromestatus, caniuse, WebKit and Mozilla standards positions, and Chrome developer docs (links inline). Failure reports came from the Obsidian forum, Logseq, SilverBullet, Excalidraw, StackEdit, Joplin and VS Code issue trackers. Rows marked *(title only)* were matched by page title and were not opened. The audit read the vault layer, service worker, boot, file recovery and the editor save path. Every defect marked **verified** was reproduced with Playwright (Chromium, OPFS browser vault) against the built app on :5200. The scripts are `probe.cjs` and `probe2.cjs` in the session scratchpad and are not part of the repo.

**Bottom line.**
- Today the app can lose or corrupt notes silently in seven ordinary situations, all reproduced (B.1):
  - failed saves are marked as done;
  - keystrokes typed in the last ~2 s before close are lost;
  - an external edit is overwritten while the note has unsaved changes;
  - two tabs on the same note overwrite each other;
  - an external delete discards the open buffer;
  - opening a note rewrites its CRLF line endings and BOM;
  - non-UTF-8 bytes are replaced with U+FFFD.
- Changes 1–7 in Part C close these and need no new platform API, just `pagehide`, IndexedDB and compare-before-write.
- The platform work that makes the app feel native comes after that, and is Chromium-desktop-first:
  - FileSystemObserver;
  - consuming `launchQueue` (the manifest already declares `.md`, but launches are ignored);
  - Document PiP pop-outs;
  - app-window shortcuts;
  - share target;
  - opt-in built-in AI.

## Part B — Robustness: how data is lost, and what this code does

### B.1 Verified defects (Playwright, built app, OPFS vault, Chromium)

| # | Scenario | Observed |
|---|---|---|
| V1 | File with UTF-8 BOM + CRLF opened, then another file opened — **no keystroke** | Bytes on disk rewritten: BOM removed, every CRLF → LF (`efbbbf23…0d0a…` → `23…0a…`). |
| V2 | Latin-1 file (`caf\xe9\n`) opened, one character typed | Saved as `caf` + `EF BF BD` (U+FFFD) — the original byte is gone for good. |
| V3 | Write rejects once (`QuotaExceededError`) during autosave, then succeeds | No notice shown; an unhandled rejection is the only trace. A later `save()` **skips** because `lastSavedData` already equals the unsaved text; disk keeps the old content until the user types again. Closing the tab now loses the edit. |
| V4 | Type, reload 300 ms later | Typed text not on disk (no flush on `pagehide`/`visibilitychange`). |
| V5 | Editor dirty, another program writes the file | External edit silently overwritten on the next autosave; no dialog, no snapshot of the external version. |
| V6 | Editor clean, another program writes the file | Editor picked the change up after **14.6 s** (15 s poll; `focus` would be sooner). |
| V7 | Same note open in two tabs, A edits then B edits | Disk ends with B's text only — **tab A's edit lost**. |
| V8 | Note named in NFD (`Cafe` + U+0301 combining acute, `.md`) on disk | Present in `fileMap` under the NFD key, but `getFileByPath()` with either NFD or NFC returns `null`, and `[[Café]]` does not resolve. |
| V9 | Editor dirty, file deleted externally, then a sync runs (e.g. window focus) | Tab closed, unsaved text discarded, file not recreated. |
| V10 | Offline reload of an installed app | `ERR_INTERNET_DISCONNECTED` — the service worker precaches nothing (`caches.keys()` = `[]`). |
| V11 | `navigator.storage.persisted()` after opening vaults | `false` (only requested when a browser vault is *created*). |
| V12 | 10,000 notes in 50 folders | Layout ready 1.24 s; each `vault.sync()` full walk 463 ms (runs every 15 s and on every focus); 10,000 separate IndexedDB `ctimes` writes on first scan. |
| V13 | One 20 MB note | Opens in 1.24 s; JS heap 624 MB; main thread busy ~2.9 s after typing three characters (save + reparse on the main thread). |

Not reproduced: an unreadable file during a scan (V-scan). Holding a `SyncAccessHandle` on an OPFS file did not make `getFile()` fail in this Chromium build, so the “scan drops a file → treated as deleted” path (adapter.ts:222 + vault.ts:314-320) is shown by code reading only. On a real folder, iCloud/OneDrive placeholder files and files locked by antivirus or a sync client are the realistic triggers.

## Part C — Prioritised changes (≤20)

Order: silent data loss first, then cross-tab and sync safety, then platform integration. “E2E” names the Playwright check that proves each fix. Every V-numbered probe above becomes a regression test in `e2e/robustness.spec.ts`.

### P0 — stop silent loss (do these first; together about 1–1.5 engineer-weeks)

1. **Save only counts once it lands** *(S, view.ts:351-359, 311)*. Move `this.lastSavedData = data` and `this.dirty = false` to after `await vault.modify` resolves. Wrap in `try/catch`. On error keep `dirty`, schedule a retry (1 s → 5 s → 30 s, then every 30 s), and call `app.saveStatus.fail(file, err)`: a status-bar item `vault-save-status` (“Saved” / “Saving…” / “Not saved: <reason>”) plus a `mod-unsaved` class on the tab header. A `NotAllowedError`/`SecurityError` from a folder vault instead opens a sticky “Folder access was lost — Reconnect” bar, whose click calls `requestPermission()` and then retries every pending save. Change `requestSave` to `void this.save().catch(report)`. E2E: V3, where the disk contains “WORLD” after the adapter recovers and a notice appears while it fails.
2. **Flush on hide, bounded debounce** *(S)*. Replace `debounce(save, 2000, true)` with a debouncer that has a 1 s idle wait and a 5 s max wait. In `App.initialize`, add `document.addEventListener("visibilitychange", …hidden)`, `window.addEventListener("pagehide")` and `document.addEventListener("freeze")`. Each calls `app.workspace.flushSaves()`, which iterates leaves whose view is a dirty `TextFileView` and calls `save()`, plus `vault` config and `requestSaveLayout.run()`. Register `beforeunload` → `preventDefault()` only while `saveStatus` has in-flight or failed writes. E2E: V4 (type, then `page.close({runBeforeUnload:true})` or reload after 300 ms, and the text is on disk).
3. **Unsaved-edit journal** *(M)*. New IndexedDB store `journal` (bump `DB_VERSION` to 4) keyed `${vaultId}:${path}`, value `{baseHash, baseMtime, text, ts}`. Write it 250 ms after each doc change in its own transaction with `{durability:"strict"}`, and delete it after a successful save. On `openVault`, list the entries; for each, read disk and hash it (SHA-1 via `crypto.subtle`). If the disk hash equals `baseHash`, show the modal “Restore unsaved changes to N notes?” (Restore writes the text, Discard deletes the entry). If it differs, open the conflict view from item 5. E2E: type, `context.close()` without waiting, reopen, and the restore prompt shows the text.
4. **Preserve bytes: EOL, BOM, encoding** *(M, adapter.ts:70,234; view.ts:337-359)*.
   - Add `vault.readText(file) → {text, format:{bom, eol, encoding}}`. Decode with `new TextDecoder("utf-8",{fatal:true, ignoreBOM:true})` and strip the BOM manually. Detect the dominant EOL by counting `\r\n` against lone `\n`. Normalise to `\n` in memory.
   - Keep `format` in a `Map<path, format>` on the vault. In `Vault.modify/process/append`, re-apply the stored format before `adapter.write`. A new file gets the vault default (`\n`, no BOM).
   - `TextFileView.save` compares against the normalised last-saved text, so an unedited file is never written.
   - When decoding fails or the file is binary (a NUL in the first 8 KB): `MarkdownView` opens read-only with a banner and a “Convert to UTF-8” button that snapshots the original bytes first (keep them in IndexedDB `snapshots` as base64 for binary).
   - E2E: V1, where the bytes are identical after open and close, and CRLF is kept after an edit. V2, where the file is read-only and its bytes are untouched.
5. **Conflict-safe save (compare-and-swap)** *(M)*. Keep `base = {mtime, size, hash}` per open file, set on load and after each own write. In `save()`, call `adapter.stat` first. If `mtime` or `size` differs from `base`, read the disk text and, if its hash differs, run `merge3(baseText, diskText, bufferText)`. Put a line-based diff3 in `packages/app/src/obsidian/vault/merge.ts`, reusing `file-recovery/diff.ts`. A clean merge writes the result, snapshots disk and buffer through `fileRecovery.forceAdd`, and shows the Notice “Merged changes made outside OpenMarkdown”. On a conflict, write nothing, snapshot both, and show a conflict bar in the view with Keep mine, Keep theirs, and Compare (opens the file-recovery diff modal with the two texts). Never accept an empty `diskText` when `baseText` is non-empty without asking. The same check runs on a `modify` event while dirty (view.ts:322), so the user learns early. E2E: V5, where the external edit survives as a merge or a prompt.
6. **Deleted/renamed underneath a dirty tab** *(S, view.ts:193-195)*. In `FileView`'s `delete` handler, if the view is a dirty `TextFileView`: snapshot the buffer, keep the leaf, set a banner “This file was deleted outside OpenMarkdown” with Recreate (calls `vault.create(path, text)`) and Close. A `create` of a same-extension file with the same size ±5% within 3 s in any folder rebinds as a rename. E2E: V9.
7. **Scan must not turn “unreadable” into “deleted”** *(S, adapter.ts:216-223; vault.ts:314-320)*. `scan()` pushes `{path, type:"file", error: e.name}` instead of dropping the entry. `sync()` treats errored entries as seen and fires no `modify`. A path missing from a scan is only deleted if it is also missing from `adapter.list(parent)` — one extra listing per missing path, capped at 200. Mass-delete fail-safe: if a single `sync()` would delete more than 20% of files (and more than 20 files), stop and show “Many files disappeared from the vault folder — is a sync client or drive disconnected?” with Rescan and Accept. Unit test via `MemoryAdapter` subclass whose `scan` throws for one path.

    - A new `conflictCopies` detector on `create` matches `/ \((?:[^)]*conflicted copy[^)]*|\d+)\)\.md$/i`, `/\.sync-conflict-\d{8}-\d{6}-[A-Z0-9]{7}\.md$/` and `/ \(Case Conflict\)/`, and only when the base file exists.
